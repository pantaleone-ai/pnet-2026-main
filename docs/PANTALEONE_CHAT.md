# Pantaleone Chat — Revised Plan (grounded in this codebase)

Strategy: two stages. **Stage 1 first** — first-party chat on
`https://www.pantaleone.net/chat`, done well. **Stage 2 only after** —
self-serve chatbots for businesses. Nothing in Stage 2 may block or
complicate Stage 1. Canonical domain everywhere for the parent brand:
`https://www.pantaleone.net`.

## 1. What the original brief assumed (and what is actually true)

| Original assumption | Reality in this repo |
|---|---|
| Separate repos `pantaleone-ai/cloudflare-rag` (Remix 2, D1, Vectorize, R2, Queues) and `pantaleone-ai/chatbot-template` exist alongside this app | Not present in this workspace. Only `pnet-2026-main` (Next.js 16 App Router, React 19) is checked out. No D1, Vectorize, R2, Queue, or Workflow bindings exist. |
| Next.js deployed via "vinext", service bindings to a separate RAG worker | Deployment is OpenNext Cloudflare (`opennextjs-cloudflare`) **plus** Vercel. `wrangler.jsonc` has only the image-cache R2 bucket and a self-reference service binding. No backend worker to bind to. |
| Auth, organizations, Stripe billing, embed.js, multi-tenant SaaS from the start | No auth provider, no DB layer, no `ai` SDK, no API-key system in the repo. Contact-form route is the closest auth-adjacent pattern (honeypot + LRU rate limit + Resend). |
| Domain `pantaleone.net` / `chat.pantaleone.net` mixed usage | Codebase canonical is `https://www.pantaleone.net` (middleware apex → www 301, `config/site.ts`, CSP, JSON-LD, contact CAPI). All new copy and URLs use `www`. |
| "Install template registry components" | shadcn/ui + Radix + Tailwind v4 + Lucide are already installed. The chat UI reuses them directly. |

## 2. Revised scope decision

Building multi-tenant SaaS (D1 schema, Vectorize indexes, Queues,
Workflows, auth, billing, embed.js, `https://chat.pantaleone.net`) inside
this checkout would require: new Cloudflare resources, secrets, DNS, an
auth provider decision, and a second deployable — none of which can be
verified from this workspace alone. That is Phase 2, explicitly gated on
owner actions (see §5).

**Phase 1 (built here): single-tenant, site-grounded chat MVP.**

- Route: `/chat` on `https://www.pantaleone.net/chat`.
- API: `POST /api/chat` — validates with zod, rate-limits 20/min/IP
  (existing `lib/rate-limit.ts` LRU, same pattern as `/api/contact`),
  retrieves context from the existing local search index
  (`lib/search-server.ts` over blog + shop content), then:
  - if `OPENAI_API_KEY` is set, streams an OpenAI-compatible
    chat-completion grounded on that context;
  - otherwise streams an honest extractive fallback that lists the
    matching pages (labeled in the UI, header `X-Chat-Fallback`).
- Streaming SSE throughout; stop/retry on the client via
  `AbortController`.
- No new infrastructure, no new dependencies, no secrets in the client,
  no fabricated citations (blog links use real slugs; products link to
  `/shop` rather than guessed deep URLs).
- Styling reuses existing tokens and shadcn components (`Card`,
  `Button`, `Textarea`) and Lucide icons. No gradients, no marketing
  language.

## 3. Files added

- `lib/validations/chat.ts` — zod request schema (message 2–2000 chars,
  history ≤ 10 items).
- `lib/chat-corpus.json` — build-time search corpus (blog + shop,
  generated by `npm run chat:corpus`). Static file because request-time
  `fs` reads return nothing on Workers; this keeps retrieval identical
  on Node, Vercel, and Cloudflare. Re-run when content changes.
- `lib/chat-retrieval.ts` — pure retrieval over the corpus (same
  weights as site search; no fs, no network).
- `app/api/chat/route.ts` — rate limit → validate → retrieve (lexical
  shortlist, embedding rerank when the AI binding is present) → stream.
  Generation priority: **Workers AI Gemma
  (`@cf/google/gemma-4-26b-a4b-it`)** → OpenAI (optional secondary,
  `OPENAI_API_KEY`) → labeled extractive fallback. `force-dynamic`,
  `no-store`, 413/429/400 handling. The server owns all provider keys.
- Retrieval rerank uses the Workers AI embedding model
  `@cf/qwen/qwen3-embedding-0.6b`: top-12 lexical pool, query + candidate
  (title + description + excerpt) embeddings in one batch call, then
  **reciprocal rank fusion** of lexical rank and embedding rank. Measured
  on the eval set: lexical 19/20, pure-cosine rerank 17/20 (demotes strong
  lexical hits), RRF 19/20 with no regressions — RRF shipped.
  `CHAT_NO_RERANK=1` forces lexical order for debugging. No Vectorize
  index — same top-K contract, no new infrastructure.
- `wrangler.jsonc` — `ai` binding plus `observability` (traces + logs,
  full sampling). Tail with `npx wrangler tail pantaleonenet [--version-id
  <id>]`. Failed invocations surface as issues in dashboard
  Observability. Note: version-preview traffic can take minutes to appear
  in tail; production traffic shows immediately.
- `cloudflare-env.d.ts` — minimal hand-written env types (AI binding
  only). Do NOT regenerate with `wrangler types`: its output redeclares
  global fetch types and breaks `tsc` in unrelated files.
- `app/(app)/(root)/chat/page.tsx` — route metadata (canonical
  `https://www.pantaleone.net/chat`).
- `app/(app)/(root)/chat/_ChatPanel.tsx` — client chat UI (messages,
  sources, suggestions, stop, error states, localStorage conversation
  history with resume/rename-free titles and delete).
- `app/(app)/(root)/chat/_ChatMarkdown.tsx` — assistant markdown
  renderer (GFM, no raw HTML; external links open in a new tab with
  `noopener noreferrer nofollow`).
- `scripts/chat-eval.mjs` — 20-question retrieval eval with ≥ 80%
  citation-hit gate (`node scripts/chat-eval.mjs <base-url>`).
- `config/navigationLinks.ts`, `app/sitemap.ts` — Chat nav entry and
  `/chat` sitemap entry.
- `lib/search-server.ts` — stopword/short-token filtering in scoring
  (shared by chat retrieval and site search; snippet extraction
  unchanged).

## Chat UI architecture (Stage 1 responsive pass)
One assistant, one backend, one conversation state, two presentations:

- `features/chat/store.ts` — message/conversation types, localStorage
  persistence (`pnet-chat:v1` + `pnet-chat:active-id`). localStorage is
  the store of record; there is no backend conversation table yet
  (Stage 2). No sensitive data is persisted.
- `features/chat/ChatProvider.tsx` — single state machine (messages,
  streaming, error + retry, popup open state). Mounted once via
  `ChatHost` in `app/(app)/layout.tsx`, so the transcript survives page
  navigation.
- `features/chat/ChatPanel.tsx` — shared transcript + suggestions +
  composer, used by both `/chat` (page variant, 800px) and the popup.
  `/chat` opened from the popup continues the same conversation.
- `features/chat/GlobalChat.tsx` — floating launcher (hidden on
  `/chat`) + responsive Sheet: **modeless** floating 420px card on
  desktop (page stays clickable/scrollable, Esc closes, launcher
  toggles), modal 92dvh bottom sheet on mobile. Panel code is
  lazy-loaded with `next/dynamic` — no chat bytes or backend calls
  until first open.
- Popup open state persists per-tab in sessionStorage
  (`pnet-chat:open`): a reload restores the chat UI as left, a fresh tab
  never auto-opens.
- `components/ScrollToTop.tsx` stacks above the launcher (same gutter,
  `lg` aligned) on pages where the launcher exists; unlifted on `/chat`.
- `components/ui/sheet.tsx` gained a `hideOverlay` prop for the
  modeless desktop panel (shared component, default behavior unchanged).
- `ChatTranscript` (collapsible sources, thinking dots, stick-to-bottom
  autoscroll), `ChatComposer` (autogrow, Enter-to-send, safe-area
  padding), `ChatMarkdown` (GFM, safe links).
- Suggestions are page-aware (`suggestionsFor(pathname)`): shop, blog,
  services/b2b/contact, and apps pages each get their own chip set;
  everywhere else gets the general set. No tracking, purely the pathname.

## Stage 2 status (2026-11-24)

**Vectorize: provisioned, seeded, evaluated — stays OFF.**
Index `pnet-chat-index` (1024 dims, cosine, 46 docs) is live and queryable.
The eval series decided its status: pure-cosine rerank 17/20, unweighted
3-way fusion 17/20, lexical+RRF 19/20 — the index leg demoted
previously-passing cases, so it stays opt-in (`CHAT_VECTORIZE=1`).
Shipped instead: **weighted RRF (2× lexical) + relevance floor with
semantic rescue**, which scored **50/50 on the live preview with zero
adversarial failures**. Query terms are punctuation-stripped; body-text
matching requires 4+ char terms ("sea" no longer matches "research");
editorial topic aliases (`KEYWORD_ALIASES` in the corpus builder,
surfaced by the mining loop) rescue slug-only topic matches. Next
experiments if quality regresses: chunked doc vectors, per-query index
fallback (leg already consults only on weak lexical top-1).

**Usage analytics: live.** Every turn writes a structured record to the
`CHAT_ANALYTICS` KV namespace (90-day TTL): per-day aggregates
(turns, paths, models, via, depth, routes, server-latency buckets,
suggestion-clicks-by-page, errors) plus raw zero-result questions
(≤200 chars, owner-approved) for search-term mining. Report:
`npm run chat:analytics` (reads the production namespace via `--remote`;
bare wrangler kv commands hit local dev storage). Two hard-won notes:
writes fire when the generation path is chosen, not when the stream
finishes — stream-finally writes silently dropped abandoned streams;
and fuzzy matching ignores tokens under 4 chars after a gibberish query
matched the stopword "for" and fabricated citations.

Weekly runbook (5 minutes): run the report, then for each question with
n ≥ 2 do exactly one of: (a) covered by an existing page → add the
query's distinctive words to `KEYWORD_ALIASES` in
`scripts/build-chat-corpus.mjs` and reseed (`npm run chat:index`);
(b) genuine gap → file a content task, do not fake coverage;
(c) off-topic/abuse → ignore (the floor + fallback handle it). Monthly:
compare suggestion CTR per page (`suggByRoute` vs `routes`); rewrite or
drop chip sets below 5% CTR. Known limits: the in-memory rate limiter is
per-isolate, so a distributed burst will not reliably trip 429s — the
`errors.r429` counter undercounts by design; true edge enforcement
needs the KV-backed limiter (Stage 2). Retention decision recorded here:
90-day TTL, question text only, no PII scrubbing yet — revisit before
any multi-tenant phase.

Adaptations from the original responsive plan: no Drawer/vaul
dependency (responsive Sheet covers both), no backend message fetch
(no D1 yet — documented Stage 2 hook), no lead-capture forms (contact
CTA only), no Message/Bubble component set (custom transcript reuses
shadcn Button/Textarea/Sheet/Skeleton/Tooltip).

## Stage 2 execution (in progress, branch `feat/chat-stage2`)

**1. Asymmetric embeddings — DONE (index re-seeded).**
`npm run chat:index [--mode compact|full]` (default compact: title +
description only, 500 chars). Compact is the fair-rematch candidate
against the full-body vectors that lost the gate. Record the active
mode here when changed. Currently: **compact**.

**2. Per-query index fallback — DONE (code).**
The Vectorize leg runs only when the lexical top-1 score is weak
(`WEAK_LEXICAL_TOP_SCORE = 10`, i.e. no title-level match) AND the
master switch allows it. Strong lexical matches skip the extra
embedding+index latency entirely. Switch: `CHAT_VECTORIZE=1` enables the
leg (default OFF until the 50-question eval beats the 20/20 baseline).

**3. Eval: 20 → 54 questions — DONE (50/50 gate, now 54 with intents).**
Paraphrase pairs, shop-product coverage, honest fallbacks
(pricing/refunds), off-topic honesty, prompt-injection resistance with
leak detection (`expectAbsent`), plus 4 permanent intent regression
tests (greeting, explore-products, hire, services). Gates: overall ≥
90%, adversarial 100%.

**4. Analytics loop — DONE (code) + weekly runbook.**
`via` (suggestion/typed/retry) and conversation-depth buckets
(first/followup/deep) flow into the KV day aggregates; `npm run
chat:analytics` prints via/depth breakdowns plus per-question coverage
hints ("possibly covered by: slug" vs "genuine gap candidate"). Weekly:
run the report, turn top zero-result questions into corpus keywords,
aliases, or new content; prune/replace suggestion chips with low
click-through (via=suggestion share falling while typed rises).

## Stage 2.5 — deterministic intents + hardening (2026-11-25)

RAG could not be trusted for the highest-value journeys: the model's
occasional empty completions rendered as blank bubbles, and the top chip
("Explore Pantaleone's products") plus the hire flow depended on
retrieval luck. `lib/chat-intents.ts` now handles greeting,
explore-products (deep product links), hire (contact card), and services
overviews before retrieval, streaming the same SSE shape. Empty model
output anywhere else falls back to the standard "couldn't find it"
message instead of silence (observed in production, logged as a warning).
UI: removed the popup "Answers from ..." footer; assistant markdown uses
default prose colors in light mode (`dark:prose-invert` only).

## 4. Verification- `npx tsc --noEmit` (must pass).
- `npx eslint` on new/changed files (must pass).
- `node scripts/chat-eval.mjs <base-url>` against a running server:
  20 questions, citation-hit gate ≥ 80%. Baseline 2026-11-23: **19/20**
  on both Node and the Cloudflare preview deployment.
  Known lexical ceiling: morphology/paraphrase near-misses (e.g.

  That gap — not a bug fix — is the evidence trigger for Stage 2
  Vectorize, which must beat this baseline on the same set.

  reads are empty on Workers, so excerpts were blank there. Fixed with
  the build-time corpus — verify by checking `excerpt` fields on the
  preview URL after every retrieval change.
- Rate limit: 20 sequential POSTs → 200, next 5 → 429 (verified
  2026-11-23 on local dev).
- Manual: `npm run dev`, visit `/chat`, ask a question, confirm sources
  render; stop mid-stream; disable `OPENAI_API_KEY` and confirm the
  fallback labels itself as index mode.
- Production deploy stays on the existing pipeline (`npm run build` /
  `npm run deploy`); no wrangler resource changes required.

## 5. Phase 2 gates (owner actions required before multi-tenant build)

Stage 2 = self-serve platform for businesses (the `chat.pantaleone.net`
vision: accounts, chatbot builder, knowledge ingestion, embed.js).
Do not start it until Stage 1 meets its definition of done (§4) and
these gates are cleared:

1. Decide auth provider (compatible with D1 + Cloudflare Workers).
2. Provision Cloudflare resources: D1 database(s), Vectorize index(es),
   R2 bucket(s) for knowledge files, KV namespace(s) for rate limits,
   Queue(s) for ingestion — per environment (dev/staging/prod).
3. Decide repository strategy: new `pantaleone-ai/pantaleone-chat` repo
   vs. monorepo route groups + `https://chat.pantaleone.net` hostname
   binding.
4. DNS + WAF/Turnstile policy for the chat hostname and embed origins.
5. Only then: D1 multi-tenant schema, persistent conversations, usage
   events, knowledge ingestion pipeline, public embed, billing.

## 6. Non-negotiables carried over from the original brief

- Server owns provider keys; browser never sees them.
- Retrieval scoped to content the requester may see (today: public site
  content only).
- No mock data presented as AI output; fallback is labeled.
- Streaming responses; persistent clean code over new dependencies.
- `www` canonical in all domains, canonical tags, and copy.
